## Outcome

The assignment’s main learner flow is now implemented as a truthful, repeatable pipeline:

`authenticated learner → personalized scenario → selected generated choice → evaluation of that exact scenario → stored authoritative result → adaptive coaching → next topic/difficulty → dashboard`

The application can run this flow with local deterministic fallbacks when Supabase, OpenAI, or the optional sentence-transformer model is unavailable. It no longer fabricates a successful frontend result or silently evaluates an unrelated wire-transfer fixture.

## Implemented Work

### 1. Authentication, authorization, and tenant isolation

- Protected scenario, evaluation, coach, dashboard, policy onboarding, and policy lookup routes with bearer-token authentication.
- Derive user ID, job role, company, and access role from the validated JWT instead of trusting browser-supplied identity fields.
- Require a configured JWT secret of at least 32 characters.
- Limited classroom accounts to explicit `CYBERGUARD_DEMO_MODE=true`; removed arbitrary `password123` account/admin creation.
- Restricted public signup to the learner role and added password length validation.
- Exchange a verified Supabase OAuth access token for the application JWT; the frontend no longer stores a raw Google token as the application token.
- Added an admin-role check before rendering the admin page.
- Added cross-user scenario isolation and tenant-aware organization-policy retrieval.

### 2. Exact scenario generation and persistence

- Added authenticated scenario ownership in the API and database schema.
- Added optional `topic` input so the Coach Agent’s recommended focus reaches the next Scenario Agent request.
- Validate generated JSON and scenario choices before returning a scenario.
- Surface persistence errors instead of claiming success when configured database writes fail.
- Added a shared process-local runtime store for a complete offline demonstration, including scenario ownership and evaluated decisions.
- The frontend requires authentication and a real generated scenario ID; it no longer substitutes a fake scenario after an API failure.

### 3. Evaluation correctness and security

- Evaluation loads the exact scenario owned by the authenticated learner; missing or cross-user scenario IDs return an error.
- The submitted action must match one of the generated scenario choices.
- Added input length validation and a per-user evaluation rate limit.
- Included non-email `channel_data` in analysis and added safe-action guidance for voice, chat, QR, OAuth, MFA, and physical-media scenarios.
- Made stored and query embeddings use the same provider: optional padded MiniLM when installed, otherwise `text-embedding-3-small`. The measured live threat/training corpus and queries both use the OpenAI model, with deterministic checked-in keyword retrieval if embedding services are unavailable.
- Derive weaknesses from actual threat indicators, reasoning classification, and channel; the fixed frontend `urgency_bias` handoff was removed.
- Made OpenAI evaluation optional so the rubric and local agents remain usable without an API key.

### 4. Authoritative adaptive coaching

- Coach processing loads the saved evaluation for the authenticated learner and ignores browser-supplied score, safety, weakness, action, and reasoning values.
- Uses the actual scenario channel and threat type when selecting remediation guidance.
- Preserves decimal evaluation scores and includes the current result in readiness calculations.
- Uses recent decision history plus the current score to select beginner, medium, or advanced difficulty.
- Forces the calculated difficulty to remain authoritative even when an LLM generates the coaching prose.
- Stores next focus, target tactic, and target channel; the frontend sends the returned topic and difficulty into the next scenario request.
- Dashboard processing now handles both list and structured-dictionary threat indicators.

### 5. Organization RAG and policy ingestion

- Policy upload is authenticated, tenant-scoped, size-limited, and restricted to PDF, TXT, and Markdown.
- Policy text is sanitized before extraction and storage.
- Custom policy retrieval prioritizes the authenticated user and company and avoids cross-tenant fallback queries.
- Improved offline policy extraction to split casual numbered language such as “first”, “secondly”, and “third”.
- Local lexical vectors are used only for local fallback retrieval; they are no longer stored as if they were MiniLM embeddings.

### 6. Database and configuration

- Added `company`, `access_role`, and `is_active` user columns plus an idempotent access-role constraint.
- Added scenario ownership and owner-only RLS policies.
- Added `match_org_knowledge`, `match_threats`, and `match_training` pgvector RPC definitions with service-role execution grants.
- Added `backend/.env.example` with Supabase, OpenAI, JWT, and explicit demo-mode settings.
- Added `backend/pytest.ini` so pytest collects the maintained suite and does not collide with the standalone script harness.

### 7. Test coverage added or updated

- Missing-token and invalid-token rejection.
- Authenticated identity overriding forged request user IDs.
- Cross-user scenario lookup and evaluation rejection.
- Unknown scenario rejection and generated-choice validation.
- Coach rejection when no evaluated decision exists.
- Coach use of the stored evaluation instead of a forged browser score.
- Protected organization and dashboard routes.
- Full scenario → evaluation → coach → dashboard integration.
- Tenant-correct policy onboarding and offline policy extraction.
