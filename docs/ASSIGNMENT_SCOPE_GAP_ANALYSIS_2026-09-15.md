## Scope to use for the assignment

The most concrete minimum is section 76, **Minimum Viable Product**, of `PROJECT PROPOSAL CyberGuard AI.pdf` (PDF pages 53–54). Its must-haves are login, learner dashboard, four specialized agents, LLM, one or two NLP techniques, RAG and a cybersecurity knowledge base, scenario generation, decision evaluation, feedback, adaptive difficulty, REST communication, RBAC, and basic security. Section 75 also expects documented evaluation results and a complete end-to-end demonstration. Section 100 (PDF pages 76–77) asks for software, documentation, a final report, and a demo.

There is a proposal conflict to settle before the final presentation: the long PDF and `docs/README.md` describe **four** specialized agents (Scenario, Security Analysis, Decision Evaluation, Coach), while `FINAL_PROJECT_PROPOSAL_2026_08_20.md`, `MID_EVALUATION_SCRIPT.md`, and the three-member contribution model describe **three** main agents, merging security analysis into evaluation. The code has all four responsibility modules, but Security Analysis is a rule-based class called inside the evaluation endpoint after the user submits an answer. The team can present three pipeline owners with four specialized components, but should state this architecture consistently and explain the timing of Security Analysis. If the submitted proposal explicitly requires four independently interacting agents, the current orchestration needs to be revised or the proposal amended with lecturer approval.

The PDF labels advanced analytics, trainer dashboard, multilingual support, voice interaction, advanced learner profiling, and LMS integration as **nice to have**. Commercial SaaS billing, multi-company production deployment, real phishing campaigns, penetration testing, malware, SOC/SIEM, surveillance, and disciplinary automation are not needed for the academic prototype. A short commercialization strategy is a written deliverable, not a product-build requirement.

## Work remaining, in priority order

1. **Make one truthful, repeatable demo path.** Choose a small representative set of threats (for example, phishing/BEC and one non-email channel). Run login → generated scenario → chosen action and written reason → evaluation → retrieved guidance → coaching → changed next difficulty/topic → personal dashboard, twice for the same user. Store and retrieve the actual scenario in the evaluation endpoint; return a clear error when an ID is missing instead of silently scoring the wire-transfer fixture. Make the demo work from a clean local setup and document the required environment variables and database seed steps.
2. **Close identity and access gaps.** Require `get_current_user` on learner data routes, derive the user ID from the validated token, and restrict policy access by organization/user. Remove permissive `password123` and arbitrary-Google-ID login paths from any non-test mode, and require a configured JWT secret. Use server-side admin/trainer guards. Keep demo accounts only in an explicit isolated demo mode. Add tests that reject missing/tampered tokens and cross-user reads/writes on every relevant route.
3. **Correct the scoring and adaptation handoff.** Evaluate the exact scenario shown to the learner; validate submitted action against that scenario's choices and cap reasoning length. Extend extraction beyond email fields for the selected non-email threat. Pass actual identified weaknesses/threat indicators into Coach instead of the browser's fixed `urgency_bias`. Have the next scenario request use the stored `next_focus` and `next_difficulty`, then demonstrate a low-score and high-score progression. Test safe, unsafe, mixed, and prompt-injection-style reasoning against expected outcomes.
4. **Prove the information retrieval contribution.** Implement or check in the three pgvector matching functions (or simplify to one documented retrieval approach). Keep the same embedding model for stored vectors and query vectors: the seed scripts pad local 384-dimensional MiniLM vectors to 1536, while `threat_retrieval.py` queries with OpenAI's unrelated 1536-dimensional vector. Confirm seeded record counts and top-k results. Attach exact source URLs/document IDs and distinguish a verified source from a broad label such as “NIST SP 800-50”. Measure retrieval relevance on a small labeled query set (for example Precision@K) and report fallback behavior separately.
5. **Demonstrate basic Responsible AI rather than claiming production guarantees.** Verify that policy text is sanitized before external LLM use and before storage if the report promises this; show clear AI disclosure, score reasoning, and a human-review flag for uncertain cases. Add a few fairness comparisons using identical actions/reasons across roles, privacy isolation tests, and prompt-injection tests. Describe zero retention, full multi-tenancy, rate limiting, TLS, and audit guarantees as future work unless demonstrably configured and tested.
6. **Finish assignment evidence and reconcile documentation.** Run backend pytest in a project Python environment with backend/requirements.txt`; add a meaningful integration test that uses the same scenario through every stage and tests authorization. Record scenario-quality judgments, NLP precision/recall or a justified qualitative sample, retrieval Precision@K, scoring consistency, agent failures/latency, and small usability feedback. Prepare a final report with architecture, actual API contract, dataset provenance, methodology, results, limitations, Responsible AI, commercialization plan, and each member's contribution evidence. Update the README's placeholder Docker, `.env.example`, and API instructions to match the runnable repository, and use one consistent three-versus-four-agent explanation.
